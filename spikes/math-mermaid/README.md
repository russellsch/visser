# Mermaid math W0 probe

This disposable probe inspected the pinned Mermaid 12.0.0 browser distribution and build-time parser paths for the proposed math feature. It changes no production code or dependencies. Results are under [`results/`](results/).

Run with Node 24 from the repository root:

```sh
node spikes/math-mermaid/browser-probe.mjs
node spikes/math-mermaid/parser-probe.mjs
node spikes/math-mermaid/katex-probe.mjs
node spikes/math-mermaid/extract-probe.mjs
```

`browser-probe.mjs` needs Chromium and permission to bind loopback. Its temporary single-file HTML is removed after the `file://` test. The other scripts are offline Node probes. The scripts save their raw observations as JSON; none is a release test or a comprehensive family inventory.

## Observed browser behavior

The exact `node_modules/mermaid/dist/mermaid.min.js` bytes copied by `scripts/build.mjs` are SHA-256 `28fca7ae6ebc7ed7bb63bde63136a74bfef14f296a57e403657eeb8b32836073`, 5,575,485 raw bytes and 1,614,349 gzip bytes. Tests ran in Chromium 153.0.8010.12 at 320 CSS pixels, `securityLevel: 'strict'`. The local HTTP probe requested only `/` and `/mermaid.js`, with zero off-origin requests or page errors. An HTML file containing the bundle once as a `data:` script loaded under `file://` in a directory with no sibling files, and a flowchart formula rendered as MathML. That file produced only its initial file request, with explicit HTTP(S) denial and zero attempted external requests. This proves these samples, not all glyphs or browser versions.

The tested formula `$$x^2$$` produced a MathML element in flowchart node, edge, and subgraph labels; state description and transition labels; sequence actor, message, and note labels; an ER relationship label; and a mindmap child label. A `\\frac{a}{b}` sample also produced MathML in flowchart and sequence labels. An invalid control sequence caused `mermaid.render` to reject in the flowchart and ER samples. The original unquoted class member sample, pie section, Gantt section, timeline event, journey title, quadrant title, and XY chart title rendered successfully **with literal `$$...$$` still in the output and no MathML**. A follow-up in-memory browser probe corrected the class conclusion: `class A["$$x^2$$"]`, `+"$$x^2$$"` inside a class body, and `+f($$x^2$$)` inside a class body all produced MathML; `A : $$x^2$$` and a bare `$$x^2$$` member remained literal. Valid class syntax can therefore use Mermaid's native math-aware label path, while grammar-specific text forms still need coverage checks. These are representative samples, not a claim about every field of each family.

The bundle source (`node_modules/mermaid/dist/mermaid.js`, around lines 23396–23439) detects `$$...$$` inside supported label rendering paths and uses bundled KaTeX with `throwOnError: true`, `displayMode: true`, and MathML output when `window.MathMLElement` exists. The source identifies KaTeX 0.16.47; the installed Node package is also 0.16.47. Its effective option call rejects `\\notacommand{x}` in the Node probe. Browser math in the tested modern Chromium needed no separate KaTeX CSS/font request. With `window.MathMLElement` made unavailable, the same flowchart rendered the text “MathML is unsupported in this environment” instead of math or original `$$x^2$$`; the default config has `legacyMathML: false`. If the runtime marks that as a successfully drawn diagram and hides the source, the accepted readable-source fallback fails. W0 must decide whether the Chromium support floor excludes that condition or how the Visser source view remains visible.

## Source-located build validation

`mermaid.mermaidAPI.getDiagramFromText` exposes parsed DB values and diagram type for all seven sampled families, including `other` families such as ER and pie. Flowchart, state, ER, class, and mindmap expose label values through `getData()`; sequence exposes actors/messages through getters. These values have **no source offsets**. Several human-readable fields sit outside the currently mapped node/edge set (for example sequence notes and diagram titles), so validating only existing Visser model labels would miss expressions.

`@mermaid-js/parser` 2.0.0 supports a subset of families through a Langium AST with CST offsets. The pie sample's `PieSection` has `label` plus a CST leaf for its label token with exact line, column, and UTF-16 offset. `extract-probe.mjs` traverses those *parsed label tokens*, then checks formulas within each token with the pinned KaTeX options. It reports the valid formula at line 2, column 3, byte offset 6 and the malformed `\\notacommand{x}` at line 3, column 3, byte offset 21. This is a proof of source-located extraction for one `other` family. It does not make pie math render: the bundle still displays literal delimiters there.

A credible full route needs a family-by-family field inventory. For Langium families, use typed AST/CST label tokens and convert their UTF-16 offsets to original source byte offsets. For legacy families without public CST spans, build a grammar-aware label-token adapter for each required family, cross-check extracted values and counts against Mermaid's parsed DB, and reject an unrecognized or mismatched construct. Validate each expression using the effective KaTeX version/options before export. Cover titles, notes, edges, subgraphs, and other rendered label fields; check duplicate labels, escaping, comments, CRLF, and Unicode offsets. Never infer complete coverage from scanning the entire fenced source for dollar pairs. The existing `getDiagramFromText` DB alone cannot meet the source-location gate.

The W0 gate is **open**. The tested families that display literal formulas need a supported math-aware diagram layout path, a deliberate redesign of the family coverage contract, or a documented blocked diagnostic until an adapter exists. A post-render string replacement would not establish label dimensions before layout. Blocking unvalidated families is an interim safety measure and does not close the “math everywhere” acceptance requirement.

## Three-family layout route

The pinned Mermaid source explains why a generic annotation overlay is insufficient. Class `addText` (`dist/mermaid.js` around lines 45295–45365) checks `hasKatex`, selects HTML labels, obtains the rendered bounding rectangle, and passes that size to `classBox`. A source-syntax inventory and formula validation adapter can use this native path for quoted members, methods, and names. It must still reject or handle class forms that Mermaid parses as plain literal text.

Pie `pieRenderer.draw` (around lines 254733–254900) puts author labels in legend SVG `<text>` with `.text(d.label)`, measures their plain-text width, and spaces legend rows at a fixed 22 pixels. The title is another SVG `<text>`. There is no premeasured HTML-label parameter. Math in a sector label or title needs a pie-specific math-aware render/layout adapter: parse the existing Mermaid pie grammar, validate source-located label tokens, measure math before positioning the legend/title, derive row heights and final viewBox from those measurements, and draw the same chart data and options. A post-render substitution can overflow both the measured width and fixed rows.

Timeline `svgDraw.drawNode` and `getVirtualNodeHeight` (around lines 271605–271680) create plain SVG `<text>` and call `wrap`, then use `getBBox` to derive each section, task, and event height. `timelineRenderer.draw` (around lines 271680–271900) uses those heights to place events and connectors; its title is also plain SVG text. There is no label-size injection parameter. A timeline-specific math-aware layout adapter (or a maintained renderer patch) must measure formulas at the node widths before computing all dependent heights and connector coordinates. An overlay or common SVG postpass cannot fix those dependencies deterministically.

`mermaid.registerExternalDiagrams` registers a detector/loader and can overwrite a detector with the same key, but it requires a whole diagram implementation (parser, DB, renderer). It is not a generic label hook, and replacing a built-in id is version-coupled. The smallest credible route under “math everywhere” is native Mermaid for proven fields plus per-family rendering adapters for unsupported fields; pie is moderate scope and timeline is materially larger. These adapters would accept Mermaid source grammar but make the final presentation Visser-owned. An upstream Mermaid renderer change could reduce maintenance later, but cannot be assumed for this release. W0 remains open until each required family field has a source-located validation path **and** a tested math-aware renderer. If that work is out of scope, the remaining gate requires an explicit user decision to narrow coverage; a literal formula or silently hidden source cannot be counted as successful rendering.
