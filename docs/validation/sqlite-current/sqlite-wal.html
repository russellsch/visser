Why SQLite readers can disagree after a commit

Snapshot · private

Snapshot captured 2026-09-29T03:22:37Z · revision f31a45ca6338 · build 86673c7a8634 · private

A commit does not refresh an existing SQLite read transaction. This example changes one counter from 100 to 80. Connection A still reads 100, while connection C reads 80. [1]

Scope: WAL mode, separate connections, and no shared cache. You need basic SQL. This page explains visibility, not crash durability or query performance.

The fixed boundary belongs to the read transaction, not each SELECT. A reader needs a new transaction to obtain a fresh snapshot. [4]

Follow A's three reads: 100 → 100 → 80. B's commit succeeds. A changes its answer only after it ends the old transaction. [1]

Check yourself B commits 60 next. A still holds the transaction that first read 100. What does A read?

Show answer

A still reads 100. Another connection's later commit does not advance A's snapshot. [4]

Change the transaction boundary, and the answer changes

Change to the experimentObserved resultWhat it distinguishes
A runs BEGIN, but delays its first SELECT until after B commits 80.A reads 80.BEGIN alone did not fix the view.
A first reads 100; B commits 80; A then tries UPDATE.SQLITE_BUSY_SNAPSHOTA cannot write from this obsolete view.
A runs BEGIN IMMEDIATE before B tries UPDATE.B gets SQLITE_BUSY; C can still read 100.A reserves the writer position early; readers can continue.

These results come from fresh databases on SQLite 3.53.0, with a zero busy timeout. [1]

Plain BEGIN defaults to DEFERRED. The first database access determines whether it starts a read or write transaction. [2]

Waiting does not refresh an obsolete snapshot. End that transaction and restart the read–decide–write operation. SQLite rejects the stale write to prevent divergent histories. [4]

BEGIN IMMEDIATE obtains the write transaction before the initial read. It can itself fail if another writer is active. This trades early writer contention for avoiding a later stale-snapshot upgrade. [2]

Check yourself A runs BEGIN but reads nothing. B commits 60. A then makes its first SELECT. Is the result 100 or 60?

Show answer

It is 60 in this scenario. BEGIN DEFERRED does not start database access; the first SELECT starts the read transaction. [2]

Definitions

BEGIN

BEGIN opens an explicit transaction. Plain BEGIN uses DEFERRED behavior; the first database access starts its read or write transaction. [2]

WAL

The write-ahead log (WAL) holds changed database pages before a checkpoint copies them into the database file. [3]

snapshot

A snapshot is the fixed database view that one read transaction uses. [4]

end mark

An end mark bounds the committed WAL content that a reader can use. It stays fixed throughout that read transaction. [3]

What this experiment does not establish

This probe does not simulate crashes, measure throughput, or exercise shared-cache read_uncommitted behavior. It uses disposable local files and explicit transaction control. Its observations establish these schedules on the recorded SQLite version.
