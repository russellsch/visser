# NATS source oracle: lost ACK in one pull consumer

Baseline: `nats-server` v2.12.0, commit `fc6ec648d806652d282d2f0edb6cb9f22c895572` in `/tmp/visser-nats-evaluation`. This is a source reading, not an executed test. Scope: one LimitsPolicy stream; one durable pull consumer with AckExplicit; two workers using that same consumer; a first delivery whose external work completed but whose ACK never reached the server. No cluster behavior is assessed.

1. **What the server knows.** Delivery records the stream/consumer sequence and adds an ACK-pending entry before sending the message (`server/consumer.go:5196-5227`, `5331-5361`). AckExplicit requires an ACK or NAK for each delivery (`server/consumer.go:330-339`). External work completion is outside this state. If the ACK did not reach the server, it cannot infer completion from that work; the entry remains pending until an ACK, termination, limit removal, or delivery-limit handling changes it. For ACK handling, the server removes a matching pending stream sequence and updates its ACK state (`server/consumer.go:3279-3331`, `3349-3350`, `3391-3398`).

2. **How worker B could receive it.** An expired pending entry goes onto the consumer's redelivery queue if it is not already queued and has not hit MaxDeliver (`server/consumer.go:5475-5570`). The next-message path takes that queue before new stream messages and loads the retained stream message (`server/consumer.go:4391-4431`). A pull delivery also needs a waiting pull request; the loop waits without one, then selects a waiting request's reply subject (`server/consumer.go:4860-4869`, `4913-4953`). Thus either worker may receive the retry depending on whose valid pull request is selected; the source does not promise worker B or immediate delivery at the exact timer boundary. A message removed from the stream before retry cannot be loaded (`server/consumer.go:4415-4429`).

3. **Delivery ceiling versus storage.** MaxDeliver defaults to unlimited (`-1`) when omitted (`server/consumer.go:566-574`). At a finite ceiling, the consumer emits a max-delivery advisory and removes its pending entry; it does not delete the stream message in that path (`server/consumer.go:2143-2171`, `5545-5551`). LimitsPolicy retains messages until a stream limit such as MaxMsgs, MaxBytes, or MaxAge applies (`server/store.go:136-146`). ACK-driven stream removal is for WorkQueue/Interest retention; `ackMsg` returns without removal for LimitsPolicy (`server/stream.go:7504-7517`). Therefore “MaxDeliver reached” means this consumer stops retrying that message, not that the message is removed from the stream. Stream limits can independently remove it, including while ACK-pending (`server/consumer.go:5510-5524`).

4. **Timeout, schedule, and NAK.** With no BackOff, AckWait sets the pending timeout; its default for AckExplicit is 30 seconds (`server/consumer.go:552-553`, `629-632`, `5492-5494`, `5525-5551`). A configured BackOff makes its first value the effective AckWait; later pending deadlines use delivery-indexed BackOff values and repeat the final value when needed (`server/consumer.go:633-639`, `5525-5543`). The BackOff length cannot exceed a finite MaxDeliver (`server/consumer.go:724-726`). A plain accepted `-NAK` queues immediate redelivery and signals new messages; `-NAK` with a valid delay schedules that delay instead (`server/consumer.go:2853-2864`, `2883-2927`). Hence ordinary NAK does not wait for the AckWait/BackOff deadline. The delayed-NAK behavior is also exercised with BackOff configured (`server/jetstream_test.go:11769-11815`). None of these timers is a bound on external work completion or an exact wall-clock delivery guarantee.

5. **Late ACK, narrowly.** An ACK arriving after AckWait but before a redelivery can still cancel the queued retry: AckExplicit matches the pending stream sequence, removes pending and redelivery entries, and updates ACK state (`server/consumer.go:3320-3350`, `3391-3398`). A test sends an ACK after its 100 ms AckWait and checks that a subsequent pull does not return the message (`server/jetstream_test.go:4029-4062`). After a retry has reached another worker, the original ACK can still match the pending stream sequence in this code; processing by that other worker may already be underway. Do not generalize the test into a guarantee that every late ACK succeeds, or that accepting one reverses external side effects.

Reader questions to test: Can the reader distinguish a pending ACK from proof of unfinished external work? Can they name the pull-request and retained-message conditions for another worker to see a retry? Do they keep MaxDeliver separate from stream retention and distinguish plain NAK from delayed NAK and timeout scheduling?
